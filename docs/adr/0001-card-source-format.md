# ADR-0001 · 卡片来源格式:保留 Quizify Markdown,结构化卡组走 JSON

- **状态**:已接受(其中挖空拆卡的描述已由 **ADR-0002** 取代)
- **日期**:2026-09-24
- **相关**:`entry/src/main/ets/data/Quizify.ets`、`Inline.ets`、`Importer.ets`

## 背景

当前的卡片来源格式是 **Quizify Card Markdown 的一个子集**。结构标记只有三个:

| 标记 | 作用 |
|---|---|
| `---` … `---` | 文件开头的 YAML front matter,声明 `quizify.deck`(`::` 表示嵌套) |
| `+++` | **切卡** —— 每张卡以它开头 |
| `***` | 切正反面 —— 上面是正面,下面是背面 |

卡内再用一批行内标记表达题型和排版:

`#### 标题`(卡内标题,用于显示与编号)、`{{挖空}}`、
`;;;` … `;;;A`(选择题块,**答案字母接在结束围栏上**)、`[[题干||答案]]`、
`[术语]^(解释)^`、`:::`(折叠)、`**粗体**`、`==高亮==`、`` `代码` ``、
`^上标^`、`~下标~`、`$数学$`、行尾 `\`(硬换行)

一共十几种标记。这确实繁琐,提出的疑问是合理的:**能不能改用 YAML?**
理由是 YAML 兼顾可读性与程序友好,而 《考研英语》那类词表本来就是 JSON。

## 决定

1. **卡片正文继续用 Quizify Markdown 子集,不迁移到 YAML。**
2. **另加一个结构化导入器,用 JSON,专门服务「短字段、无行内排版」的卡组**
   (词表型:单词 / 音标 / 释义 / 例句)。它与 Markdown 导入器并存。
3. 缓解「太复杂」的办法是**文档化一个最小档位**,而不是换格式(见下)。

## 理由

**一、没有缺陷需要用换格式来修。**
`devtest/sync-and-test.mjs` 当前 8/8 套件全过,其中解析器一套 44 条断言全过。
里面覆盖的正是 YAML 会重新引入的那些坑:行首 `#` 是标题但句中 `C#` 不动、
`$x^{2}$` 里的 `^` 不当上标、数学段里的 `**` 不当粗体、跨行挖空计数连续。
这些断言是真金白银的工作量,换格式等于把它们置于风险之中,换来的是零个已知 bug 的修复。

**二、YAML 只能替换外层容器,替换不了行内标记。**
这是最关键的一点。改成 YAML 之后,卡片仍然要表达「这里挖空」「这四个是选项」
「这段是公式」—— 这些标记必须原样活在 YAML 的字符串里。
YAML 能替掉的只有 front matter(本来已经是 YAML)和 `####` 这一行分隔符。
也就是说,**被抱怨的复杂度几乎全部留在原地**,而代价是一个新解析器。

**三、ArkTS 运行时没有 YAML 解析器,而 `JSON.parse` 是内置的。**
npm 上的 `js-yaml` 依赖 ArkTS 受限的动态特性,不能假定可以直接跑。
选 YAML 意味着自己手写解析器;选 JSON 是零成本。

**四、YAML 的经典陷阱对考试文本格外不友好。**

| 陷阱 | 对题库的后果 |
|---|---|
| 裸标量里的 `: ` 会截断 | 「下列说法正确的是:」直接解析失败 |
| `#` 起注释 | `#include`、`#define`、C# 被吃掉半行 |
| Norway problem:`no/yes/on/off/y/n` 解析成布尔 | 答案写 `no`、选项标 `N` 会静默变成 `false` |
| Tab 不能用于缩进,多行需 `\|` 块标量 | 手写者最常翻车的地方 |

Markdown 出错的后果是渲染略歪;YAML 出错的后果是第 400 行解析中断。

**五、结构化格式确实有它赢的场合:短字段、规则、无行内排版。**
词表正是如此,手改 YAML/JSON 比在 Markdown 里排版舒服得多。
所以结论不是「Markdown 全胜」,而是**按卡组类型分工**。

## 最小档位(用来回应「不需要弄得那么复杂」)

写一副卡组真正必需的只有三样:front matter 的 `deck`、`+++` 切卡、`***` 切正反面。
下面这份是**实机验证过能导入的**最小例子:

```markdown
---
quizify:
  deck: 数据结构::第二章
---

+++

#### 2.1 线性表的顺序存储

顺序表按下标随机访问的时间复杂度是多少?
***
$O(1)$ —— 元素地址可由下标直接算出。
```

题型只需三选一:

- **纯问答** —— 正面问、背面答(如上)
- **选择题** —— 正面放 `;;;` 块,答案字母接在结束围栏上(`;;;A`)
- **挖空** —— 正文里写 `{{答案}}`,一张卡上所有的空同时考(ADR-0002)

其余标记(`[[..||..]]`、`[..]^(..)^`、`:::`、上下标、高亮、硬换行)**全部可选**,
是排版糖,不写完全不影响导入。文档应当明确这一点 —— 现在的印象是
「这十几种都得学」,而实际要学的是三个结构标记 + 一种题型写法。

> 教训:本 ADR 初稿把 `####` 当成切卡标记,照它写出来的示例导入直接失败
> (`导入失败:第 6 行: 整份文件里没有任何 +++,一张卡都没有`)。
> 文档里的格式示例必须实机导入过再写进来。

## 影响

- 新增导入器只需产出 `ParsedDeck`,交给 `Importer.storeDeck(db, parsed, ...)`;
  数据库、两套排期引擎、复习界面都不用动。格式之争因此不是架构之争。
- 若日后真有手写结构化卡组的需求,可以在同一个 seam 后面补一个
  **严格 YAML 子集**解析器(约 200 行:只认 `key: value`、列表、`|` 块标量,
  并强制引号、拒绝裸标量),规避上表的陷阱。本 ADR 不排除这条路,只是不先走。

## 未采纳的方案

- **全面迁移到 YAML**:理由二和理由三足以否决 —— 收益接近于零,成本是一个解析器。
- **迁移到 JSON 作为唯一格式**:JSON 不支持注释、不支持多行字符串,
  教材型内容(公式、代码块)手写体验比 Markdown 差得多。

## 实机验证(2026-09-24,模拟器 127.0.0.1:5555)

一份覆盖全部题型与行内标记的测试卡组走完了导入 → 复习 → 评级 → 落库:

| 环节 | 结果 |
|---|---|
| 导入 | `已导入 6 张卡到「测试::第一章」` |
| 拆分 | 4 个 `+++` → `notes=4`;含 3 个挖空的那条展开成 3 张 → `cards=6` |
| 卡组嵌套 | `测试::第一章` → `decks=2`(父 + 子) |
| 行内渲染 | `**算法**` 渲染为「算法」,`` `n` `` 渲染为「n」,标记符未泄漏到正文 |
| 数学 | `$O(\log n)$` 按原文显示 —— 符合 CONTEXT.md「v1 推迟 KaTeX」的决定 |
| 评级 | 四档 忘了/困难/良好/简单;「良好」→ `下次 10 分钟后` |
| 落库 | `scheduling` 与 `review_log` 各 1 行,S=2.307 D=2.118 reps=1 phase=1 step=1,due 恰为 10 分钟后 |

两点观察,不属于本 ADR 范围,另记:

1. 答完一张仍显示「剩 6」。因为该卡进入 10 分钟学习步进、今天还会回来,
   计数不减是自洽的;但用户看不到「我刚答对了」的反馈。
   WordSnap 用绿/灰/白三段条解决过同一问题(见 CONTEXT.md 经验 5)。
2. `scheduling` 行在首次作答时才创建,导入后为 0 行。是惰性建行,不是缺陷。
